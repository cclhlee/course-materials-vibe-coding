# 練習2：資安修補PR撰寫練習——從codeBuggy到codeGood

> 第13週：實作工作坊②：資安修補與多重視角同儕程式碼審查 — 對應簡報「練習2：資安修補PR撰寫練習——從codeBuggy到codeGood」段落，實作時段：100-140分鐘

## 學習目標

練習閱讀一段已修補的diff片段，撰寫一則完整說明修補理由與驗證方式的PR留言，並在自己專案repo中完成至少一項真實資安修補

## 操作步驟

1. 先閱讀下方codeBuggy（修補前）與codeGood（修補後）的用藥時程新增功能程式碼片段，找出兩者之間的具體差異。
2. 依照第1.1節PR描述範例的格式（修補了什麼/為什麼/如何驗證），為這個diff撰寫一則PR描述。
3. 回到自己（或延續用藥提醒系統）的Replit專案，重新執行第12週介紹的npm audit（或ZAP Baseline Scan），從掃描結果中選擇至少一項尚未修補的弱點或警示項目進行修補。
4. 在GitHub上開立正式的PR，撰寫符合「修補了什麼/為什麼/如何驗證」格式的PR描述，並附上修補前後的掃描結果數字對照。
5. 與同組同學互相在對方PR的Files changed分頁留下至少1條逐行diff留言，練習指出具體行號與具體疑問。

## 測試資料

| 修補前風險 | 修補後做法 | 驗證方式 |
| --- | --- | --- |
| 字串拼接SQL，有SQL Injection風險 | 改用參數化查詢（$1,$2...） | 嘗試在藥名欄位輸入含單引號的字串，確認不會造成資料庫錯誤 |
| 必填欄位可留空送出 | 後端加入必填欄位檢查 | 留空必填欄位送出，確認回應400與提示訊息 |
| 資料庫錯誤沒有回應 | 加入err判斷回傳500訊息 | 刻意送出錯誤格式資料，確認前端收到明確錯誤訊息而非卡住 |

## 提示（卡關時再看，上課前請勿提前公布）

- 撰寫PR描述時，「為什麼」不要只寫『比較安全』，要具體指出原本的字串拼接方式為什麼會有SQL Injection風險。
- 「如何驗證」建議具體寫出你實際測試時輸入了什麼資料、預期看到什麼結果，而不是只寫『測試過了，沒問題』。
- 如果你的專案暫時沒有明顯的高風險弱點可修補，可以選擇ZAP Baseline掃描結果中的WARN-NEW項目（例如補齊某個安全性標頭）作為練習對象。

## 討論問題

- 同儕在你的PR留言中，最常指出你哪一類問題（例如描述不夠具體、還是程式本身仍有疑慮）？
- 比較codeBuggy與codeGood，除了SQL Injection風險，你還發現哪些細節差異（例如錯誤處理、必填檢查）？
- 如果沒有事先閱讀diff，只是整段複製貼上codeGood，你覺得自己會不會注意到參數化查詢與必填檢查這兩個改動背後的理由？
