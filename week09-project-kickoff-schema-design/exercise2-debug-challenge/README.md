# 除錯挑戰：找出刻意設計錯誤的Schema問題

> 第9週：專案啟動：需求分析與資料庫schema設計 — 對應簡報「除錯挑戰：找出刻意設計錯誤的Schema問題」段落，實作時段：130-145分鐘

## 學習目標

練習在一個刻意包含多重正規化與schema設計錯誤的範例中，找出至少3個具體問題並提出修正建議，強化辨識常見設計缺陷的能力。

## 操作步驟

1. 四人一組，檢視下方「錯誤範例schema」，這是一個管理長者用藥與家屬聯絡資訊的系統，但刻意包含多個常見設計錯誤。
2. 先各自獨立找出至少3個問題，再向組員口頭說明每個問題屬於哪一類（資料重複、缺外鍵、缺NOT NULL、資料型態不合理等）。
3. 討論並寫出每個問題的具體修正建議，可參考本週第2、3節的正規化與約束檢查方法。
4. 全組合力產出修正後的schema版本，並與下方「參考修正方向」核對，確認修正理由都能清楚口頭解釋。

## 測試資料

| 表名 | 刻意設計的問題 | 問題類型 |
| --- | --- | --- |
| 使用者表 | 姓名同時重複存在使用者表、用藥時程表、服藥紀錄表 | 資料重複（違反正規化） |
| 用藥時程表 | 沒有使用者ID外鍵，只存使用者姓名字串 | 缺外鍵約束 |
| 服藥紀錄表 | 服用日期用VARCHAR自由輸入文字存日期 | 資料型態不合理 |

## 提示（卡關時再看，上課前請勿提前公布）

- 判斷是否有資料重複的關鍵：同一項資訊（如姓名）是否出現在超過一張表？如果是，應該只留在最原始的來源表，其他表改用外鍵參照。
- 判斷是否缺外鍵的關鍵：某張表是否用「文字」（如姓名字串）去對應另一張表的記錄，而不是用該表的主鍵ID？這種寫法無法保證資料一致，也無法用資料庫的外鍵約束防止錯誤資料。
- 判斷日期型態是否合理的關鍵：如果欄位需要排序、比較大小或做日期區間查詢，就不該用VARCHAR/TEXT儲存，應該用DATE、TIME或TIMESTAMP等日期時間型態。

## 討論問題

- 這三種錯誤中，哪一種如果沒被發現，會在專案後期造成最大的修改成本？為什麼？
- 如果你們是負責審查別組schema的角色，除了這三類問題，你們還會優先檢查哪一項？
