# 除錯挑戰：找出「一次性生成」CRUD程式碼中的錯誤

> 第10週：後端開發：AI協作實作CRUD功能 — 對應簡報「除錯挑戰：找出「一次性生成」CRUD程式碼中的錯誤」段落，實作時段：120-140分鐘

## 學習目標

練習辨識AI一次性生成、包含常見CRUD錯誤的程式碼——SQL Injection風險的字串拼接、忘記處理Update找不到資料的情況、Delete忘記加WHERE條件，並提出修正版本，銜接第12週資安主題。

## 操作步驟

1. 四人一組，檢視下方「錯誤版本」的三段CRUD程式碼（分別對應Create/Read、Update、Delete），這些程式碼是老師示範「一次性要求AI生成全部CRUD功能」時得到的結果。
2. 針對第一段程式碼，討論字串拼接使用者輸入的藥名會有什麼風險，並寫出使用參數化查詢的修正版本。
3. 針對第二段程式碼，討論如果時程ID打錯、找不到對應資料時會發生什麼事，並修改成會回報「查無此筆時程」的版本。
4. 針對第三段程式碼，討論如果這段DELETE被誤執行在正式環境會發生什麼後果，並寫出加上WHERE條件的修正版本。
5. 全組合力找出至少2-3個問題後，與下方「修正版本」核對，並練習針對每一處修正說出對應的「口頭三句話說明」。

## 測試資料

| 錯誤類型 | 風險等級 | 後果 |
| --- | --- | --- |
| 字串拼接SQL | 高風險（資安） | 使用者輸入可被解析成額外SQL指令，可能查出或竄改不該存取的資料 |
| Update找不到資料未處理 | 中風險 | 使用者誤以為修改成功，實際上舊資料仍在系統中繼續生效 |
| Delete忘記WHERE | 極高風險 | 整張資料表所有記錄被刪除，且通常無法復原 |

## 提示（卡關時再看，上課前請勿提前公布）

- 判斷是否有SQL Injection風險的關鍵字：只要看到用+號或樣板字串把「使用者輸入」直接接進SQL字串裡，就該提高警覺。
- Update是否需要檢查結果，可以用「如果這個ID不存在，程式會不會告訴使用者」這個問題來檢驗；PostgreSQL的RETURNING子句是很好用的檢查工具。
- 檢查Delete語句時，養成「有DELETE FROM就一定要找WHERE」的反射動作，執行前務必先用相同WHERE條件跑一次SELECT確認影響範圍。
